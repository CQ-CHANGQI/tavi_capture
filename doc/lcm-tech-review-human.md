# LCM 实时链路评审（草案）

LCM 这块前阵子重写了。老代码是从参考仓库搬过来的，叠了好几版，光看文件就得先捋半天，这次索性按协议重新拆了一遍。

评审主要看三件事：**组播怎么收、分片怎么拼、线程怎么分**。协议字段、平台权限这些我尽量一句话带过，细节都在代码里。

## 先说背景

机器人那边相机走 `239.255.76.67:7667`，关节走 `239.255.76.68:7668`。现场是 60Hz，四路 640×360 JPEG，正常一帧几十 KB，压测的时候我拿 150KB 的图跑过。

平板这边目标就一个：尽量跟住 60fps，跟不上就丢帧，**不能越播越慢**。之前那版有 33ms 合并定时器，60Hz 进来也只能出 30fps，这个已经删了。

## 1. 组播接收

相机和关节各一条 socket，绑 `0.0.0.0`，`reuseAddress` 打开。相机链路会顺手把 `/preview/joint_batch` 也加进去，因为有些发布端（包括我们的 mock）把关节和相机发在同一组；如果机器人关节是单独的组/端口，再开第二条链路。

| 数据 | 组 | 端口 |
|---|---|---|
| 相机 | 239.255.76.67 | 7667 |
| 关节 | 239.255.76.68 | 7668 |

**join 要挨个网卡加，这是重点。**

组播成员关系是按网卡的，不是按机器。之前只 join 默认路由那块，现场就是“Wi-Fi 能看，插上网线黑屏”。现在每 2 秒扫一遍 `NetworkInterface.list()`，新插的网卡、新起的 VPN 都会补 join；也可以 `LCM_IFACE=en6` 固定一块网卡，排查的时候好用。

收包循环一次最多连收 512 个，然后主动让出事件循环。不这么做的话，数据一密集，定时器和停止命令都排不上队。

平台这块：

- Android 要 `MulticastLock`，不然息屏/后台就被过滤，Manifest 里权限已经加了。
- iOS 要 Apple 的 `com.apple.developer.networking.multicast` entitlement，我们现在没放（放了没权限签名会挂），所以 **iOS 上目前收不到组播**，这个得走申请。
- macOS 沙箱给了 `network.client/server`，实测能收。
- Windows 记得放行 UDP 7667/7668 入站。

收不到数据的时候先看两个数：

1. `datagrams` 是不是 0。是 0 就是包根本没到本机，查网段、端口、join、防火墙。
2. `interfaces` 是不是空。空就是一块网卡都没 join 上，常见于 VPN 抢路由或者 `LCM_IFACE` 写错。

通道名不确定就 `LCM_ALL=true` 先全收，确认有没有包、通道叫什么，再回来改配置。

## 2. 分片组包

这里其实有**两层分片**，别混在一起看。

第一层是 LCM 自己的长包。UDP 一包放不下的大消息，LCM 会拆成：

```text
magic(LC03) | seq(4) | total(4) | offset(4) | index(2) | count(2) | channel\0? | chunk
```

**通道名只在第 0 片。** 这个坑很深，按“每片都带通道”去解的话，真实的多片消息会全部丢掉。我们按 `发送方:端口 + seq` 分组，通道名从第 0 片补。

判完整不是看“片数够了”。片是往固定缓冲区里按 offset 写的，最后要检查字节是不是从 0 连续覆盖到 total，重叠片、空洞片都算坏包。之前只数片数，理论上能拼出一条中间有洞的消息。

上限：同时最多 64 个半包，单条消息 512KB，2 秒收不齐就扔。重复片直接忽略；同一个 seq 的 total/count 变了，整组丢掉。

第二层是 `preview_package_t`，相机帧和关节包都会切成最多 1200 字节的片：

```text
hash(8) | messageId(8) | streamId(4) | index(4) | count(4) | total(4) | length(4) | payload
```

这层校验比较硬，发送端契约不满足就直接丢，连缓冲区都不进：

- `count == ceil(total / 1200)`
- `length == min(1200, total - index * 1200)`

每路相机最多同时留 3 个半成品。丢了一片的那帧就废了，不能卡着后面的帧。`message_id` 比已经完成的帧旧的直接丢，不然迟到的旧片能再拼一张旧图出来。

拼完还要看 JPEG/PNG 头，不是图就记 `corrupt`，不交给 UI。

关节包有两种到法：裸的 `joint_batch_t` 直接解，或者用 `preview_package_t` 包一层再解（机器人 joint bridge 是后者）。`joint_batch_t` 是 10 个固定槽位、每个 128 宽，实际数量看 count；我们只读 count 个 double，剩下跳过，只留 `/position` 的项，按关节名对齐。

异常处理的原则就两条：**坏片不进缓冲，坏帧不交 UI**。具体每个分支都计了数，`parseErrors`、`dropped`、`incomplete`、`corrupt` 分开记，现场好定位。

## 3. isolate 线程模型

接收全在后台 isolate 里做：socket、LCM 分帧、两层重组、关节解码、统计。UI isolate 只拿完整帧和关节批次，负责解码、上屏。

这么分的原因不复杂：

- 收包和重组是纯 CPU/IO，放后台，UI 不卡。
- 单个坏包或者某个流异常，影响不到 UI 事件循环。
- 接收端能独立统计、独立排查。
- UI 只处理“完整画面”，逻辑简单，不容易出幺蛾子。

UI 侧每路相机只有**一个 latest 槽**，不是队列：

```text
latest[相机] = 最新一帧
解码线程取走 latest 去解
解码期间来的新帧直接覆盖 latest
```

所以每路最多一张在解、一张在等。解码慢就丢中间帧，但延迟不会越积越大。

这块我们试过两个方案，都放弃了：

- **排队逐帧解码**：60Hz 跑几分钟延迟就上来了，画面越看越旧，不行。
- **ack 背压**：UI 收一批回一个 ack，接收端最多 N 批在途。实测 26KB/60Hz 下带 ack 只有 57fps 左右，不带能到 59.6；150KB 大帧抖得更厉害。ack 往返的抖动比它省下的发送更亏，最后改成接收端直接发、UI 端丢帧。

跨 isolate 的代价也说一下：每帧字节要复制一份到 UI isolate，26KB×4×60 大概 6.2MB/s，150KB 的话 36MB/s。我拿 292MB 数据量过 `TransferableTypedData`，94ms 对 80ms，只快 15%，摊到每帧大概 1%，所以没上，不想为这点收益加一层所有权管理。

真正的瓶颈在 UI 解码，不在拷贝。所以现在源宽超过 1280 才按 1280 解，正常 640×360 不缩放。

生命周期很简单：接收 isolate 建好 socket、join 完网卡发 `ready`；UI 发 `stop` 就关 socket、停定时器。统计每 500ms 推一次，`datagrams / messages / parseErrors / dropped / incomplete / corrupt / pending / interfaces`，页面和 `tool/live_check.dart` 用的是同一套。

## 几个还没定的，评审时想听听意见

- iOS 的 multicast entitlement 谁去申请、多久能下来。这个不解决，iOS 端 LCM 就是不可用。
- 150KB/60Hz 在 debug 构建下只有 50 出头，release 还没正经测过。如果现场就是大帧，是降到 960 宽解码，还是干脆上原生解码，得定个方向。
- 通道名不统一：机器人那边有 `camera_fisheye_l`，我们这边习惯 `cam_left`。现在 `LCM_ALL` 会做一层名字归一，但固定订阅还是按 `cam_*`。要不要让机器人侧统一，还是我们长期维护映射。
- 无 ack 的代价是 UI 卡的时候 SendPort 里可能短暂堆一点消息。UI 处理每帧是 O(1)，实际没出过问题，但如果要求硬上限，就得把 ack 捡回来。
